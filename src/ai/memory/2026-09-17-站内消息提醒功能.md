# 站内消息提醒功能（2026-09-17）

> 对话开始：2026-09-17 12:45　对话结束：2026-09-17 13:07（UTC+8）

## 需求背景

顶部栏的 `MessageBtn` 一直是**纯占位**（只有图标 + `v-perm`，`<script setup>` 为空，无逻辑无接口）。本次要把它做成可用的站内消息中心：

- 触发：① 用户评论文章 → 通知文章作者；② 回复自己的评论 → 通知被回复人
- 展示：TopBar 点击出下拉看最近消息，「查看全部」→ 个人中心看全部
- 状态：已读 / 未读，支持全部已读，角标显示未读数
- 后续可能扩展点赞 / 收藏

用户确认的决策：

| 决策点 | 结论 |
| --- | --- |
| 触发范围 | **三种**：文章被评论 / 你的评论被回复 / 文章下的「回复别人」也通知文章作者（留言板天然覆盖） |
| 点击跳转 | 后台「评论管理」页，带 `sourceId` **定位并高亮**该评论 |
| 桌面弹窗 | **不做**，只做角标 + 下拉（待办弹窗是因为有「到点」语义，新消息没有） |
| 个人中心 tab 数字 | 显示**未读数**（与角标一致），非总数 |
| 后端归属 | 新建 app `modules/notice`，不并入 `modules/user` |

## 关键发现与分析

### 1. 后端零基础设施，挂钩点唯一

全库搜索确认**没有任何通知相关的 model / 接口 / signals**（命中的都是 `django.contrib.messages`、`AiMessage`、`UserTask.remindBeforeMinutes` 这类无关项）。评论创建是纯手工 `Comment.objects.create()`，**没有 post_save 信号**，所以通知只能在 `modules/client/comment_views.py` 的 `add_client_comment` 里显式挂钩。

接收人不必新写逻辑：`modules/comment/service/comment.py` 已有 `get_target_author_id()`（`article` → `Article.author`；`message` → `BloggerProfile.userId`），直接复用。

> **整个方案依赖 `Article.author` / `BloggerProfile.userId` == 博主后台登录账号的 `id`**。`can_delete_comment` 已依赖同一假设——若评论管理的「删除」按钮在博主账号下能用，前提即成立；否则博主会收不到任何消息。

### 2. 数据模型：不存内容快照，只存 id + 关系

`blog_notice` 只存 `recipient / sender / type / sourceId / targetType / targetId / rootId / isRead / readTime`。

规划时权衡过用 JSONField 存评论摘要快照（项目里 `UserMood.images`、`BloggerProfile.assets` 有先例），最终**否掉**：快照省不了几次查询，却会带来数据不一致（评论删了通知里还留着正文）；改为列表接口用 4 次固定查询（通知分页 + 批量评论 + 批量用户 + 批量文章标题）组装，评论被删/被隐藏时**自然降级**为「该评论已删除」，符合项目已有的 batch-map 惯例（`build_user_map` / `build_article_title_map`）。

其他取舍：**不加 `isDelete`**（首期不做单条删除）；`sourceType` 字段现在就建，为将来的点赞/收藏留口子。

### 3. 通知推导规则（去重与优先级）

在 `service/notice.py` 里收成一个纯函数 `build_comment_notices()`，返回 `[(recipient, type)]`：

- 顺序即优先级：`replyUser` 的 `comment_reply` 排在 `target_author_id` 的 `article_comment` 前面
- 同一接收人只保留先命中的一条 → 回复的恰好是文章作者时，只发 `comment_reply`，不重复发
- `recipient == sender` 一律跳过 → 博主评论自己的文章、作者回复别人都不会给自己发

### 4. 定位跳转需要给既有接口加参数

`/comment/list` 原本不支持按 id 查询，只靠关键词/对象/时间筛选 + 分页，命中不了指定评论。加了可选 `focusId`：传回复 id 时**返回到它所属的顶层评论**（`Comment.objects.filter(id=focus.rootId)`），保证前端渲染时能连回复一起看到；定位是精确查询，直接覆盖其它筛选项。

前端用 `watch(() => route.query.focus)` 而非 `onMounted`——评论管理页会被 keep-alive 复用，已在页面上时再点一条消息不会重新挂载。

### 5. 新增 `notice:refresh` 事件作为统一刷新信号

角标、个人中心 tab 数字、消息列表三处都要在「已读」后刷新，但分属不同组件。统一约定：任何已读操作都 `emitter.emit('notice:refresh')`，三处各自**具名 handler** 监听。

`off` 时**必须带 handler**。代码库里 `TaskList.vue` 的 `emitter.off('task:refresh')` 省略了 handler，会一次性摘掉该事件的所有监听（包括 `useTaskReminder` 的），不要再复制这个写法。

### 6. 坑：`v-perm` 不能放在 `el-popover` 上

原占位组件把 `v-perm` 放在根 div 上，改造时若顺手挪到 `el-popover` 上会失效——`el-popover` 的根是 fragment / 非元素节点，Vue 的运行时指令无处挂载（控制台会警告 "Runtime directive used on component with non-element root node"）。正确做法是放在 `#reference` 插槽里那个 div 上。

6. 后台的 `MessageBtn` 文案/间距在本次对话后由用户微调过 `TopBar/index.vue`，与功能无关。
