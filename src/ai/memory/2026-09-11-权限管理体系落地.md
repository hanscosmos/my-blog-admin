# 权限管理体系落地（L2：菜单 + 操作级 RBAC）（2026-09-11）

> 对话开始：2026-09-11 20:18　对话结束：2026-09-11 21:39

## 需求背景

博客后台此前只有「菜单管理」和「角色管理」两个独立页面，**角色 → 菜单/操作权限的分配链路完全不存在**，只有超级管理员和普通用户两种角色，所有登录用户实际拥有全部权限。

用户要求做实质性权限开发，并确认了方案边界：

- **L2 层级**：菜单可见性 + 页面内操作权限
- **后端强制校验**：配置映射表（路径 → 权限码），未映射路径默认放行
- **废弃** `Api` 接口权限体系和「接口管理」页面，删除后端 `Api` / `ApiAuthority` 模型相关全部代码
- 超级管理员角色 `code = 10000`，不可更改、不可删除、不可授权
- 权限变更时机：登录时拉取，角色变更后需重新登录
- 普通用户默认只有读权限，敏感信息的读权限也不给，全部由超管分配

开发完成后用户又发现两个问题，均在本次对话内修复。

## 关键发现与分析

### 1. 权限链两端都是断的

前端 `Role/index.vue` 的「权限分配」按钮误绑到了删除操作，`DistributeAuthorityDialog` 组件根本没被 import；同时前端调用的后端路由（`setRoleInterfaceApi` 等）后端也并不存在。属于「两边各写了一半、从没通过」的状态。

### 2. 复用 `Menu` 表，按钮作为 `type='3'` 叶子节点

不新增权限表。`sys_menu.type`：`'1'` 目录 / `'2'` 页面 / `'3'` 按钮。**`type='2'` 页面节点 = 查看权限**（决定侧边栏与路由可见性），**`type='3'` 按钮节点的 `code` = 操作权限码**，命名 `模块:资源:动作`。这样授权 UI 仍然只是一棵 el-tree，不需要两套模型。

### 3. 受控路由的判定

`permission/self` 接口返回 `menuRoutes`（所有菜单声明过的页面路由 name）。前端路由守卫**只拦截这些路由**，未声明的（`ArticleDetail`、`UpdateArticle` 等详情页）放行，由页面内的按钮权限控制入口。避免详情页无法访问。

### 4. el-tree 父子联动无法表达「仅查看」——本次最核心的坑，踩了两轮

用户诉求：「有些菜单我允许查看，但无法编辑」。

- **第一版（错）**：回显时用 `collectParentIds` 把「有子节点的节点」从已授权 id 中剔除，只 `setCheckedKeys` 叶子。后果：「只授权了页面、没授权任何按钮」——正是"仅查看"——页面节点因"有子节点"被剔除，结果**一个都没勾上**；管理员再点确定提交空数组，查看权限被静默清掉。
- **第二版（仍错）**：改用后序遍历 + `setChecked(id, true, false)`（`deep=false` 不级联）。回显修好了：只授权页面时父节点能渲染成勾选态（`setChecked` 里 `allWithoutDisable` 为 false 时不会把 `checked` 打回 false）。但**交互路径依然坏**——用户点击取消子节点走的是 `node.setChecked(false, deep=true)`，会触发 `reInitChecked(parent)`，而 `reInitChecked` 在「子节点全部未勾选」（`none === true`）时把父节点 `checked = false`（`element-plus/es/components/tree/src/model/node.mjs:38-40` 与 `:359-365`）。所以取消最后一个操作，「查看」必然跟着掉。
- **结论**：**联动开着的时候，「查看独立于操作」在这棵树上根本无法表达**，只能关掉 `check-strictly`。

### 5. Pinia「no active Pinia」——导入时机被提前

`src/utils/request/index.ts` 在**模块作用域**执行 `const request = new Request('base')`，而构造函数里调用了 `useUserInfoStore()`。Pinia 的 active 实例只在 `app.use(pinia)` 时通过 `setActivePinia()` 设置（`createPinia()` 本身**不**设置，已核对 `pinia/dist/pinia.mjs`）。

原来该模块只被懒加载路由的 `api/**` 拉起，所以恰好满足"pinia 已装"。新增的静态导入链把它提前了：

```
main.ts → import router → router/index.ts → hooks/usePermission
        → api/authority/permission → utils/request → new Request() → 💥
```

这条链在 `main.ts` 的 `createPinia()` 之前就完成求值。属于**原本就存在的脆弱点**，被新导入链暴露。

### 权限分配对话框的最终形态（改动前必读）

- **必须 `:check-strictly="true"` 关掉父子联动**，否则「仅查看」配不出来（原因见「关键发现 4」）。
- 联动关掉后自己补两条规则（`onCheck`，`@check` 只在用户点击时触发，程序化 `setChecked*` 不触发，所以回显/全选不会误触发）：
  - 勾选时 `checkAncestors` 补祖先（侧边栏树需要父级才能挂载）
  - 取消时 `clearDescendants` 清子孙（页面不可见时其操作权限无意义）
  - 两条都**不向上取消**：取消一个页面不会连带取消它的目录（否则会误伤同目录其他页面）
- 回显：`setCheckedKeys` 前先 `await nextTick()`（避免设在旧节点实例上），并用 `withAncestors` 补齐祖先（兼容历史数据「只授权按钮、没授权页面」）。
- 提交：`menuIds = getCheckedKeys()`（严格模式无半选态）。
- 顶部有「全选 / 清空」——严格模式下勾全量需要逐个点，用它兜底。
- 树节点带类型标签：`目录` / `查看` / `操作`。

## 后续注意事项

1. **必须执行迁移**：`cd my-blog-service && ./.venv/bin/python manage.py migrate`。0007 会写入 40 个按钮权限节点，依赖对应父菜单已存在（找不到父菜单的会跳过）。
2. **迁移后超管需重新登录**才能拿到新的权限码。
3. **历史授权数据可能已被写坏**：在 `check-strictly` 修复之前，凡是按「取消所有操作」方式保存过的角色，其查看权限已被空数组覆盖，需要重新配置。
4. **「不允许查看」目前只由前端保证**（菜单不下发 + 路由守卫 + `v-perm` 隐藏）。读接口未纳入 `PERMISSION_PATH_MAP`，绕过前端直接调 `xxx/list` 仍能拿到数据。需要服务端也挡读时，在映射表补 `xxx/list → 对应页面权限码`。
5. **新增后端写接口必须同步登记映射表**，否则默认放行。
6. 菜单表里若仍有 `route='InterfaceManage'` 的旧记录，点击侧边栏会报「该路由尚未添加」，建议删除。
7. **`utils/request` 现在会被 router 静态拉起**，任何在模块顶层直接调用 `useXxxStore()` 的写法都会重现 "no active Pinia"。规则：store 只在函数/回调内取。
8. 已知既有 TS 错误（与本次改动无关，未修复）：`SysSettings`、`ArticleTag/TagDialog`、`User/Activity`、`TaskTable`、`HotArticle`、`WorkBench/Home`。

## 减少 Token 使用的建议

1. **本次最大的浪费是反复整读同一个文件**。`DistributeAuthorityDialog.vue` 被完整 Read 了多次；改代码用 `Edit` 精确替换即可，不必先 Read 全文。
2. **排查第三方库行为时不要猜**，但也别整文件读——直接用 `grep -n` 定位到函数名，再 `sed -n 'A,Bp'` 取那几十行（本次查 el-tree 的 `setChecked` / `reInitChecked` 就是这么做的，很省）。
3. **遍历目录清单用 `git status --short` / `grep -rn`**，不要用 Read 打开目录。
4. **长对话中途及时 `/log` 或 `/clear`**：本次会话上下文被压缩过一次，压缩后的摘要会作为输入反复重发，缓存读取量因此很高。
5. 验证阶段把 `vue-tsc` 的输出 `grep` 成只看关心的文件（`grep -i "DistributeAuthority"`），避免成批的既有错误刷进上下文。
