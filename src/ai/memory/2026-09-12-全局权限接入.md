# 全局 / 非侧边栏页面的权限接入（2026-09-12）

> 对话开始：2026-09-12 14:16　对话结束：2026-09-12 14:41（UTC+8）

## 需求背景

昨天落地的 RBAC 只覆盖了「左侧菜单 + 菜单对应路由页面」的权限，**没有任何地方在管全局性的操作入口**：

- 顶部导航栏：待办事项提醒、消息、AI 助手
- 系统设置按钮（`SysSettings` 齿轮）
- 个人中心内部三个 tab（动态 / 创作 / 事项）里的操作按钮

这些页面/入口不在左侧菜单树里，因此既无法在「角色管理 → 权限分配」的树里勾选，也没有权限码可供 `v-perm` 判断。用户的核心诉求是：**要有一套能自定义这类特殊页面（不在侧边栏的页面、或纯全局入口）权限的机制**。

确认过的方案边界：

| 决策点 | 结论 |
| --- | --- |
| 建模方式 | 给 `Menu` 加一个「是否侧边栏显示」布尔字段，不新增节点类型 |
| 个人中心的路由 | 只控入口 + tab 内按钮，**不**把 `UserCenter` 加进受控路由 |
| 默认授权 | 种子只建节点、不发授权，全部由用户手动分配 |
| 个人中心粒度 | tab 本身常显，只控 tab 内的操作按钮 |
| 后端强制校验 | 个人中心的写接口**只做前端控制**，不登记 `PERMISSION_PATH_MAP` |
| 种子范围 | 现有全量菜单树 + 新的「全局」子树 |
| 文章相关动作 | 复用已有的 `article:add/update/delete` |
| 系统设置 | 只卡齿轮入口，抽屉里的各个开关不再细分 |

## 关键发现与分析

### 1. 为什么用 `isNav` 而不是新节点类型

`MenuFormDrawer` 的 `type` 是由父节点推导的（`parseFloat(fatherMenuItem.type) + 1`），也就是 `sys_menu` 的三级结构在表单层就被写死了。想表达「全局」这种第四类节点，新增 type 会直接破坏表单与授权树的渲染逻辑。

改用 `Menu.isNav`（`db_column='is_nav'`，默认 `True`）：

- `isNav=True`：原有的目录/页面，照旧下发给侧边栏
- `isNav=False`：仍然是一棵正常的三级子树，**照常参与角色授权**，只是「全局」目录整体不下发给侧边栏

于是「全局」被建成：`全局`(目录 type='1', isNav=false) → `待办事项提醒 / 消息 / AI 助手 / 系统设置 / 个人中心`(type='2', isNav=false) → 个人中心下挂 6 个 `type='3'` 操作按钮。授权树里它和普通菜单长得一模一样。

### 2. `type='2'` 页面节点也要能携带权限码

新增的全局入口大多是**非路由页面**（比如「系统设置」只是个抽屉），没有前端路由，只有权限码。为此在 `permission.py` 里引入：

```python
PERMISSION_CODE_TYPES = (MENU_TYPE_PAGE, MENU_TYPE_BUTTON)

def get_user_permission_codes(user_id):
    """当前用户的权限码集合（页面 + 按钮节点，目录不计）"""
```

让 `global:setting:open` 这类页面级 code 走和按钮码完全相同的 `hasPerm(code)` 通道，前端只需要一个 `v-perm`。

注意 `has_permission()`（后端强制校验那条路径）**有意保持不变**，仍然只认 `type='3'`。本次决定个人中心写操作不做后端校验，若将来要补，把它的类型判断一起放宽到 `PERMISSION_CODE_TYPES` 即可。

### 3. 侧边栏过滤必须在 SQL 层做，且必须用 `filter` 而不是 `exclude`

`get_user_nav_menu_ids` 会用 `with_ancestors` 把父级补回来。如果只 `exclude(isNav=False)`，被排除的「全局」子节点会被祖先补全逻辑**重新拉回侧边栏**。所以 `get_nav_menu_tree` 里写成：

```python
Menu.objects.filter(isNav=True).exclude(type=MENU_TYPE_BUTTON)
```

### 4. 全局节点必须 `route` 留空

`get_all_menu_routes()` 完全没动。全局节点 route 为空 → 永远不会变成受控路由 → 既不需要额外的路由白名单，也顺带满足了「个人中心不进路由拦截」的决策。

### 5. 迁移编号撞车（踩到的坑）

数据库 `django_migrations` 里 `authority` 已经注册到 **0007**：

- `0002`~`0004`：2024 年的老迁移（`apiauthority_isforbidden`、`menu_level_alter_menu_icon` 等）
- `0005`~`0007`：昨天权限体系那批（`drop_api_and_add_role_issuper`、`backfill_super_role`、`seed_button_permissions`）

一开始按目录里看到的文件数编了 `0002/0003`，会和另一台开发机上的记录撞车。已重命名为 **`0008_menu_isnav` / `0009_seed_menu_tree`**，并清掉数据库里两条错误的 `django_migrations` 记录后 `migrate authority --fake` 校正。**以后新增 authority 迁移请从 0010 起编号。**

## 后续注意事项

1. **非超管角色现在看不到顶部导航栏任何按钮、设置齿轮和个人中心入口**，需要在「角色管理 → 权限分配」里手动勾选「全局」子树。权限是登录时拉取的，分配后需重新登录才生效。
2. **个人中心的写接口没有后端校验**（本次刻意只做前端隐藏），`PERMISSION_PATH_MAP` 里没有登记，接口直接调用仍然可用。将来要补后端强制时，需同时放宽 `has_permission()` 的节点类型判断。
3. **`.gitignore` 里的 `migrations/` 是用户有意排除的**（迁移文件累积多了会让命令执行混乱，用户不信任迁移文件），所以本次两个迁移文件不会进版本库。本次真正的交付物是数据库里多出的 12 条节点，已在本地库完成；换环境重建库时需要注意菜单树可能为空。
4. 新增 authority 迁移请从 **0010** 起编号，避开 `django_migrations` 里已注册的 0002~0009。
5. `v-perm` 隐藏元素用的是 `display:none`（不删除节点，避免频繁重渲染时 vdom/DOM 不匹配），因此不要依赖它做安全边界。
6. 已知既有 TS 错误（与本次无关，未修复）：`SysSettings/index.vue(19,16)`、`TaskTable.vue(84,85)(90,93)`、`HotArticle.vue(45,11)`。

1. **导出数据不要往终端打印中文**。本次为了生成种子迁移把 `sys_menu` 全量导成 JSON 文件再 Read，避免了控制台乱码；但生成迁移时其实是脚本直接写文件更省——只在需要核对时读片段即可。

3. **改代码用 `Edit` 精确替换**，避免「先 Read 全文再改」的组合。
4. **验证阶段把 `vue-tsc` / `build` 输出 grep 成只看关心的文件**，别让成批既有错误刷进上下文。
