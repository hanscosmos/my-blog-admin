# 语音录入重复生成修复与标点恢复停用（2026-08-14）

> 对话开始：2026-08-14　对话结束：2026-08-14 19:46

## 需求背景

文章页语音录入（`Article/components/VoiceInputBar`）存在两个问题：

1. 每次点「停止」按钮，说的一段话被**重复生成两次**。
2. 中文识别结果的**断句/标点很差**，用户认为「有它不如没有」，要求：若有更好算法就换，否则把现有方法注释掉。

## 关键发现与分析

- **重复生成根因**（`src/hooks/useSpeechRecognition.ts`）：`recognition.stop()` 会触发一次 `onresult` 事件，把当前临时识别内容以 `isFinal: true` 追加进 `rawFinalText`（`onresult` 里已处理）。而原 `stop()`/`pause()` 又手动把 `interimText` 合并进 `rawFinalText`。由于 `onresult` 是**异步**触发，手动合并时 `interimText` 尚未被清空，于是同一段话被写入两次。
- **中文标点无更好前端算法**：Chrome 的 Web Speech API 对中文**不返回标点**（英文才有），只能靠后处理"猜"。中文断句需要语义理解，纯规则法必然频繁误插，已是天花板，不是规则写得不够好。
- **真正有效的方案都需额外资源**（非前端简单换算法）：
  - 换自带标点的云端 ASR（讯飞/阿里/腾讯/百度等），效果最好，需后端对接、有费用。
  - 后端接入标点恢复模型（PaddleNLP 标点模型 / `ct-punctuation`）或把识别文本丢给 LLM 加标点。

## 改动清单

| 文件 | 改动 |
|------|------|
| `src/hooks/useSpeechRecognition.ts` | 1. 删除 `stop()` 与 `pause()` 中手动把 `interimText` 合并进 `rawFinalText` 的代码（重复生成根因），改为只依赖浏览器 `onresult` 的最终结果；2. `finalText` 由 `computed(() => restoreChinesePunctuation(rawFinalText.value))` 改为 `computed(() => rawFinalText.value)` 直接返回原文；3. 用块注释停用整个 `restoreChinesePunctuation` 函数，注释内写明停用原因与改进方向 |
