# 后台评论管理功能（2026-09-17）

> 对话开始：2026-09-17 12:15　对话结束：2026-09-17 12:42（UTC+8）

## 需求背景

博客前台的评论能力（发表 / 删除）已经上线，评论表 `blog_comment` 也已建好，但**后台完全没有任何评论管理入口**。本次要补上：

- 后台能查询评论、能删除评论，**不做修改、不做新增**（发评论只在前台）
- 评论对象是多模块的：目前是 `article`（文章）与 `message`（留言板）
- 评论正文是 **markdown 源码**，后台要能完整渲染查看
- 管理员看到违规评论后，可以**直接禁用该用户**（写 `Users.isForbidden`）

确认过的方案边界：

| 决策点 | 结论 |
| --- | --- |
| 删除方式 | **软删除**（复用 `isDelete`，与前台一致，可回溯） |
| 列表结构 | 顶层评论一行，回复**嵌在内容格里**（不用 el-table 树形，理由见坑点 2） |
| 禁用副作用 | **只置 `isForbidden=true`，不动其历史评论** |
| 菜单节点 | 由用户在「菜单管理」界面手动加，代码里不加 seed 迁移 |
| 前端落点 | 页面归到**系统管理**模块（`views/pages/System/Comment`，路由加进 `router/modules/System`） |
| 权限码 | `system:comment:delete`、`system:comment:forbid-user`（跟随页面所属模块） |

## 关键发现与分析

### 1. 后端现状：模型齐全，但后台侧一个接口都没有

`modules/comment/` 下只有 `models.py` + `serializers/` + `service/`，**没有 views、没有 urls**。现有评论接口全部是前台的，放在 `modules/client/comment_views.py`，挂在 `/client/comment/{list,add,delete}`，靠 `targetType + targetId` 限定对象，删除权限是「评论作者本人或内容作者」。

所以后台要新开一套：不做对象限定，删除权限**完全交给权限码**，不复用前台那个 `can_delete_comment()`（规则完全不同，混用会串）。

`COMMENT_TARGET_TYPES`、`is_valid_uuid`、`build_user_map` 这些则直接复用。

### 2. `Users.isForbidden` 存在，但全项目没有任何接口能写它

```
$ grep -rn "isForbidden" modules --include="*.py" | grep -v __pycache__
modules/user/models.py:13        isForbidden = models.BooleanField(default=False, ...)
modules/user/views/user.py:94    if user.isForbidden: return res_handle(500, '该用户已被禁用！')   # 读
middleware/auth.py:29            if user.isForbidden: return JsonResponse({'code':401,...})      # 读
```

字段、登录拦截、中间件拦截都已就绪，**只缺写入入口**。本次新建 `POST /comment/forbid-user`（带安全校验：不允许禁用自己、不允许禁用超管）。

### 3. 菜单节点没有可复用的种子迁移

`PROJECT_GUIDE.md` 提到「全局子树由迁移 `0009_seed_menu_tree` 种下」，但**该文件在仓库里并不存在**。`modules/authority/migrations/` 只有 `0001`~`0007`，其中 `0007_seed_button_permissions` 只种 `type='3'` 按钮节点，且是**按 route 匹配已有父节点、匹配不到就跳过**（说明页面节点历来是在界面里手动建的）。

因此评论管理的菜单节点也交给用户在「菜单管理」界面加，代码侧不引入新迁移。**指南这一处描述与实际不符，属于文档漂移。**

### 4. 接口路径前缀与权限码前缀本来就不绑定

现有先例：`/user/add` → `system:user:add`、`/blogger/profile/update` → `system:blogger:update`。所以评论接口放在 `/comment/*`（`modules/comment/views.py`）而权限码用 `system:comment:*` 并不冲突，**以页面所属模块为准**。这一条已补进 PROJECT_GUIDE 的接口前缀约定。

### 5. 坑：弹窗组件必须套 `<div v-if="formDialogProps.visible">`

现象：分页（`AppSearchPanel` 的 `#footer`）**被滚上去，不再固定在下边**。

根因：`AppDialog` 的根元素是 `div.app-dialog.w-full.h-full`。页面根是 `<div class="wh-full">`（普通 block），里面已经放了占满 100% 高的 `AppSearchPanel`；再把对话框无条件渲染进去，等于在它后面又塞一个 100% 高的块 → 页面内容 200% 高 → 外层 `.content-wrapper`（`flex-1 h-0 overflow-auto`）被撑出滚动条，固定底部自然跟着滚走。

项目里**每个**带弹窗的页面都写成：

```html
<div v-if="formDialogProps.visible">
  <XxxDialog :visible="formDialogProps.visible" ... />
</div>
```

以前容易以为是「重置组件状态」，真正原因是**布局占位**。新增弹窗页面务必照抄这个写法。

### 6. 坑：el-table 树形的展开箭头会独占第一列

最初用 `row-key` + `:tree-props="{children:'replies'}"` + `default-expand-all` 做两级展示，实测两个问题：

- 箭头渲染在**第一列左侧**，即使该行没有子节点，第一列也会预留那一段槽位，视觉上像「箭头独占了一列」
- 缩进默认只有 16px，回复和顶层几乎看不出层级差别

另外**空的 `children: []` 也会渲染一个点不开的展开箭头**（当时的绕法是前端 computed 把空数组置成 `undefined`）。

最终改为**不用树**：表格只渲染顶层评论（`:data="dataList"`），回复由 `CommentThread` 组件嵌在「评论内容」单元格内渲染（左侧 2px 竖线 + 12px 缩进，每条回复自带时间与操作）。代价是去掉了「回复对象」列（回复对象内联在回复行里）。

### 7. 删除一条 SQL 覆盖「选中项 + 其下回复」

```python
Comment.objects.filter(isDelete=False).filter(
    Q(id__in=ids) | Q(rootId__in=ids)
).update(isDelete=True)   # 返回值即删除条数
```

比「先查回复 id 再 update 两次」少一轮查询，且天然幂等（回复的 id 不会出现在别人的 `rootId` 里，不会误伤）。

### 8. 扩展共享 serializer 的边界

`build_user_map` 的 `.values()` 里加了 `isForbidden`（后台需要，用于切换「禁用/解禁」文案）。前台 `format_user()` 只取 `id/nickName/avatar` 三个键，多返回一个字段对前台**无影响**，所以直接改共享函数而不是复制一份。

## 减少 Token 使用的建议

1. **三仓库探查先 grep/find 定位、再读片段**，不要整文件 Read。本次后端 `client/comment_views.py` + service + serializer 一次读完（合计约 250 行）是必要的；但 `models/user.py`、`authority/models.py`、`0009/0007 迁移` 都是先 grep 命中行号再截取，省了不少。
2. **决策一次问全**。用一次 `AskUserQuestion` 把「删除方式 / 列表结构 / 菜单节点怎么加 / 禁用副作用」4 个问题一起问掉，避免 4 轮往返。
3. **视觉类需求先给带预览的方案让用户选**，别先实现再返工。本次「层级展示」给 3 个 ASCII 预览后一次定稿；若直接按自己的判断写，返工成本是一次完整重写 + 一次 build。
4. **验证输出 grep 过滤**：`npx vue-tsc > /tmp/x.log` 再 `grep -i comment`，别让既有的 10 个错误每轮刷进上下文。
5. **长对话及时 `/log` 或 `/clear`**：本次缓存读取 1900 万，压缩摘要会随每轮请求反复重发，是缓存读取量的主要来源。
